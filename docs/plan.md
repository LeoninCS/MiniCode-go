### 注意

## Day 13：上下文压缩触发与摘要 ✅

### 目标

避免长任务导致上下文无限增长。

### 内容

- ✅ 使用最近一次主对话 usage 校准上下文占用，并估算新增消息、工具参数、结果和工具声明；
- ✅ 固定 `ContextWindow = 256 * 1024`、`ReservedTokens = 16 * 1024`，剩余空间严格小于余量时触发压缩；
- ✅ 在每次模型请求前检查预算，包含本次新用户输入；工具执行期间等待完整批次结果追加后再检查；
- ✅ 保留系统 Prompt，摘要使用目标、约束与偏好、进度、关键决策、下一步和关键上下文的结构；
- ✅ 固定 `KeepRecentTokens = 20000`，按完整消息和工具批次选择接近预算的边界，不提供配置项；
- ✅ 使用当前 Provider 的独立、无工具 `Chat` 请求生成摘要，借用 pi 的首次和更新摘要模板；
- ✅ 完整序列化旧用户消息、assistant 文本、工具名称、参数、调用 ID 和结果，摘要输入不做固定字符截断；
- ✅ 摘要输入超预算时按 UTF-8 边界分块，每块更新已有摘要；服务端上下文超限时拆小当前块继续处理；
- ✅ 修改文件、测试状态、已知错误与后续工作由 LLM 归纳到进度和关键上下文中，暂未提供独立元数据字段；
- ✅ 手动 `/compact`、自动压缩、上下文超限恢复共用同一函数；主对话超限仅重试当前模型请求一次，不重新执行工具；
- ✅ 摘要调用和 usage 计入任务统计，成功更新检查点后清空旧预算校准，下一次主对话回复重新校准；
- ✅ 手动压缩成功后立即保存，自动压缩和超限恢复在本轮结束时保存；恢复完整原始消息与检查点，模型只读取摘要和近期原文；
- ✅ 摘要失败、为空、被输出长度限制截断、返回工具调用或被取消时，保留压缩前历史；没有可压缩旧内容时不调用模型。

20k 是近期原文的近似目标，始终至少保留最新的一条完整消息或工具批次；这个整体本身很大时，保留量可能超过 20k。会话保留边界不拆协议消息，摘要请求的文本分块可以跨消息或参数文本，但不会省略剩余内容。

256k 是代码中的固定窗口假设，未自动读取所用模型的实际窗口。最新输入本身过大或最新工具批次无法放入模型窗口时，历史压缩不保证请求一定成功。

### 产出

实现见 `apps/internal/compaction/trigger.go`、`compact.go`、`prompt.go` 和 `apps/internal/agent/compact.go`。测试见 `apps/test/compaction/trigger_test.go`、`compact_test.go`、`apps/test/agent/compact_test.go` 与 `apps/test/cli/compact_test.go`，覆盖阈值、完整输入、滚动更新、分块、工具配对、失败与取消、统计校准、超限恢复不重放工具及手动压缩存档恢复。`go -C apps test ./...` 已通过。

- 同一条项目约定可以查看、更新和删除，重复保存不会产生重复条目，已失效或删除的信息不会继续注入；
- 新的用户指令可以覆盖旧记忆，记忆中的文件位置和命令会结合当前项目状态验证；
- 记忆文件损坏或写入失败有明确提示；失败写入保留原文件，普通任务仍可按当前输入和会话历史执行。

### 产出

```text
会话 A：确认测试命令和项目约定 → 保存项目记忆
会话 B：提出新任务 → 读取相关记忆 → 检查当前项目 → 执行并验证
```

项目记忆复用经过整理的知识；任务续接使用 Session 保存的有效历史，长对话的长度控制仍由上下文压缩负责。

## Day 16：Subagent 任务委派与独立上下文 ⬜

### 目标

主 Agent 可以把一个明确的子任务交给独立的 Agent 执行，并接收结果。例如，主 Agent 负责修复问题，子 Agent 负责阅读某个模块并找出相关调用链。

### 内容

- 定义子任务请求，包含任务目标、必要背景、工作区和期望返回内容；
- 为子 Agent 分配独立 ID，并记录父会话 ID，关联一次委派和对应结果；
- 复用现有 Provider 和 Agent Loop，以独立消息历史运行子任务，不启动 CLI 输入循环；
- 子 Agent 使用专用系统 Prompt，只接收主 Agent 提供的任务背景及选出的相关项目记忆，不自动复制父会话全部历史；
- 为主 Agent 注册 `delegate_task` 工具；先实现一次委派、等待完成、结果回传的完整流程；
- 首个版本子 Agent 仅开放 `read` 工具，代码修改和 bash 执行由主 Agent 统一处理；子 Agent 不开放委派工具，委派深度固定为一层；
- 子任务继承父任务的取消和剩余时限，并设置独立模型轮数上限；
- 返回明确的完成、失败、超时或取消状态，以及结论、文件位置、依据和未解决的问题；
- 主 Agent 将子任务结果作为委派工具的结果写入历史，再决定下一步，不把子 Agent 全部消息合并到父上下文；
- 使用 Fake Provider 覆盖委派参数、上下文隔离、工具权限、结果回传和失败路径。

### 验收标准

- 主 Agent 可以委派一次模块分析，并基于子 Agent 的结果继续回答或调用工具；
- 父子消息历史互不混入，子 Agent 无法调用未开放的工具或再次委派；
- 子任务失败能作为工具结果回传主 Agent，不强制终止整个父任务；
- 父任务取消时，子任务的模型请求同步取消，文件句柄等资源得到释放。

### 产出

```text
用户要求修复问题
→ 主 Agent 委派“分析相关模块与调用链”
→ 子 Agent 独立阅读并返回结论与文件位置
→ 主 Agent 结合结果修改代码、运行验证并回答用户
```

## Day 17：Subagent 并行调度、过程展示与恢复 ⬜

### 目标

支持同时处理多个互不依赖的分析任务，让用户能看到子任务进度，并能统一取消和汇总结果。

### 内容

- 增加子任务管理器，维护排队、运行、完成、失败、超时和取消状态；
- 支持批量委派独立子任务，配置同时运行的数量上限和单次委派数量上限，超出并发上限的任务排队；
- 按任务 ID 等待和收集结果，允许部分子任务失败，主 Agent 能区分成功结果与失败原因；
- 每个子任务独立管理消息历史、工作区句柄和输出事件；沿用只读工具范围，由主 Agent 统一执行修改；
- 父任务取消时停止排队任务，并取消所有运行中子任务；等待它们退出后再结束父任务；
- 为整项父任务设置模型调用总预算，覆盖父子 Agent，防止增加子任务后绕过资源限制；
- CLI 按子任务 ID 展示开始、完成和失败状态，统一处理并发输出，避免多个 goroutine 同时读取 stdin 或直接写终端；
- 汇总父子任务耗时、模型调用和 token usage；子任务数据计入父任务一次，缺失 usage 沿用现有不可用或部分统计语义；
- 保存父子关联、子任务状态和已完成结果；恢复会话时，原先排队或运行的任务标记为已中断，由主 Agent 决定是否重新委派，不自动恢复进程；
- 使用 Fake Provider 和可控制的阻塞点验证并发上限、排队、结果归属、部分失败、取消、统计及恢复行为；对并发路径运行 race 检查。

### 验收标准

- 两个独立模块分析可以并行执行，运行数量始终不超过配置上限；
- 一个子任务失败时，其他子任务仍可完成，主 Agent 能拿到全部结果和状态；
- Ctrl+C 能停止所有子任务，退出后没有遗留 goroutine 或正在执行的模型请求；
- 父任务统计不会漏计或重复计算子任务用量，非交互 stdout 仍只输出主 Agent 的最终回答；
- 恢复会话后可以查看已完成的子任务结果，并明确识别中断任务。

### 产出

主 Agent 可以并行委派“分析配置加载”和“分析会话恢复”，等待结果后给出统一结论，并继续完成代码修改和验证。

## Day 18：Langfuse / OpenTelemetry 会话追踪、效率分析与失败诊断 ⬜

### 目标

按 Session 回看 MiniCode 的任务过程，展示主 Agent 与 Subagent 的调用关系，定位失败原因及耗时和 Token 消耗较高的环节。

### 内容

- 将本地 Session ID 关联到 Langfuse，每轮任务保持独立 Trace；跨进程恢复后仍归入同一 Session，形成连续的会话时间线；
- 为主 Agent、子任务、模型请求与工具执行建立父子 Span，传递 OpenTelemetry context，并记录 Agent ID、父任务 ID、轮次和状态；
- 使用 Langfuse 的 Agent 图与时间线展示委派、并行执行和结果汇总，点击记录可查看输入、回复、工具参数、结果及错误；
- 区分模型等待、审批等待、工具执行和子任务排队的耗时，支持定位慢请求与失败步骤；
- 按 Agent 和模型汇总模型调用次数、输入与输出 Token，并统计工具耗时、重复读取和连续失败重试；
- 根据模型价格配置估算成本；缺少 usage 或价格时标记为不可用或部分统计，父子任务用量只累计一次，任务总耗时按实际起止时间计算；
- CLI 可输出对应的 Trace / Session 查看链接；非交互模式写入 stderr，保留 stdout 的最终回答；
- 保持追踪可选，上传失败不阻断 Agent 任务，关闭追踪时不影响原有执行与会话恢复；
- 从 MiniCode 自身的失败记录中提炼最小文件样例、工具结果或固定模型响应，补充到现有 Agent、工具和 CLI 回归测试；
- 通过本地 OTLP 接收端验证 ID 关联、父子关系、并发任务归属、错误状态、用量聚合与退出刷新。

### 验收标准

- 同一 Session 在两次进程启动中的任务能归到同一会话时间线，历史记录不会因恢复而重复上传；
- 一个包含两个并行 Subagent 的任务能展示完整调用关系，并定位各子任务的模型和工具调用；
- 可以识别最慢步骤、Token 消耗最多的 Agent，以及重复读取或持续重试的任务；
- 典型失败能定位到具体模型或工具调用，并通过本项目自动化测试复现和验证修复；
- 缺失数据不会被显示为零成本，追踪服务不可用时任务仍可完成，非交互输出保持可供管道处理。

### 产出

从一个 Session ID 进入执行记录，查看“用户任务 → 主 Agent → 子 Agent → 模型 / 工具 → 汇总回答”，并比较各步骤的耗时与用量。

会话回看使用已记录的数据；任务执行与存档恢复仍由 MiniCode 管理。展示能力参考 Langfuse 的 [Sessions](https://langfuse.com/docs/observability/features/sessions)、[Agent Graphs](https://langfuse.com/docs/observability/features/agent-graphs) 和 [Token & Cost Tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)。
