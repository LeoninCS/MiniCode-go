# MiniCode-go 项目规格说明

> 状态：Draft  
> 范围：v0.1 项目规格

## 1. 项目概述

MiniCode-go 是一个使用 Go 从零实现的、以 CLI 为主要交互入口的轻量级 Coding Agent，可以理解为一个面向原理学习的“迷你版 Pi”。

用户通过命令行向 Agent 描述编码任务，Agent 通过大语言模型理解任务，并在用户授权的前提下使用本地工具浏览代码、修改文件、运行测试，最后返回任务执行结果。

项目希望实现的核心闭环是：

```text
理解任务
  ↓
检查代码
  ↓
制定下一步动作
  ↓
调用工具
  ↓
读取工具结果
  ↓
修改或继续分析
  ↓
运行验证
  ↓
总结结果
```

## 2. 项目定位

### 2.1 教学型项目

MiniCode-go 的主要目的不是打造一个功能最全的商业 Coding Agent，而是通过一个规模可控的项目学习以下内容：

- 模型如何调用工具；
- Agent Loop 如何工作；
- 模型、Agent 和工具之间如何分工；
- 如何让模型观察代码并采取行动；
- 如何将工具错误反馈给模型并继续恢复；
- 如何控制文件修改和命令执行权限；
- 如何验证 Agent 是否真的完成了任务。

### 2.2 简单但完整

项目会尽量减少外部框架、复杂抽象和非必要功能，但不会只实现一个“调用模型然后打印答案”的聊天程序。

首版至少应包含：

- 模型适配器；
- Agent Loop；
- 工具注册和分发；
- 文件浏览和搜索；
- 文件修改；
- 命令执行；
- 人工审批；
- 错误处理；
- 停止条件；
- 基础测试和运行日志。

### 2.3 CLI 优先

CLI 是项目首版唯一需要重点支持的交互方式。

CLI 既支持一次性任务，也支持同一会话内的多轮交互，例如：

```text
> 先分析一下这个项目的结构
> 重点看看 parser 相关代码
> 按照刚才的分析修复问题
> 运行测试验证一下
```

首版不考虑 Web UI、IDE 插件或后台常驻服务。

### 2.4 本地工作区优先

Agent 主要服务于本地代码仓库：

- 一次处理一个工作区；
- 文件操作限制在工作区范围内；
- 命令默认在工作区中执行；
- 不自动访问其他项目或远程环境。

## 3. 项目目标

### 3.1 首要目标

实现一个可以完成以下任务链的最小可用 Agent：

```text
用户提出任务
→ Agent 阅读相关代码
→ Agent 找到需要修改的位置
→ 用户批准后修改文件
→ Agent 运行测试或检查命令
→ 根据结果继续修复
→ Agent 汇报修改和验证结果
```

### 3.2 学习目标

通过项目理解：

- 对话上下文和任务状态；
- 工具定义和结构化参数；
- 模型调用与工具结果回传；
- 宿主程序对模型行为的控制；
- 代码编辑策略；
- 测试驱动的 Agent 工作流；
- 安全边界和权限审批；
- Agent 的可观测性和评测方法。

## 4. 功能范围

首版版本暂定为 `v0.1`。

### 4.1 CLI 任务入口

CLI 需要支持：

- 从命令行参数接收一次性任务；
- 从标准输入接收任务；
- 启动交互式多轮会话；
- 指定工作区路径；
- 指定模型名称和模型服务地址；
- 设置最大 Agent 轮数；
- 设置任务超时；
- 用户主动取消任务；
- 输出过程事件和最终结果。

截至 2026-10-02，交互终端已支持多行编辑、自动折行、光标移动和随光标滚动。`Shift+Enter` / `Ctrl+J` 插入换行，`Enter` 提交整段输入；上下键只在当前输入的显示行之间移动，到首末行停止，不浏览历史记录。管道输入保持逐行提交。

Ctrl+C 在输入阶段退出且不提交草稿，在运行阶段取消底层操作并退出整个会话。用户取消显示「任务已中断」，任务达到时限显示「任务执行超时」，普通失败保留具体错误；上述状态不代表本节其他规划项均已完成。

### 4.2 会话和上下文

首版需要在单次进程运行期间保留当前会话上下文，包括：

- 用户消息；
- Agent 的阶段性回答；
- 模型工具调用；
- 工具执行结果；
- 工具错误；
- 当前工作区信息。

当前实现会为新会话生成 UUID，并默认将历史自动保存到工作区内的 `.minicode/sessions/<id>.json`。CLI 启动时显示该 ID；后续可在同一工作区使用 `--session <id>` 跨进程恢复。存档包括用户消息、Agent 回复、工具调用与结果、工作区和上一轮状态；恢复时重新生成系统 Prompt，不恢复运行中的进程、审批状态或文件读取缓存。

Session v2 保存完整原始消息 `messages`，并独立保存压缩检查点 `compaction`，包含摘要 `summary` 和近期消息起点 `first_kept_message_index`。压缩只更新检查点，内存和存档中的原始历史继续保留；模型请求临时构造摘要与近期原文。手动 `/compact` 成功后立即保存，自动压缩和超限恢复沿用本轮结束时的保存流程。存档继续受 64 MiB 文件大小限制。

读取 v1 存档时会迁移到 v2；旧摘要移入独立检查点，现存原始消息继续保留。旧版已经被摘要替换而丢弃的原文无法恢复。恢复时校验完整原始历史和检查点，再构造模型上下文。

该能力属于显式恢复的会话历史，不等同于跨会话长期记忆。

### 4.3 上下文压缩

上下文压缩属于 Coding Agent 的基础能力之一，但首版只实现轻量级方案，不引入向量数据库或复杂记忆系统。

上下文压缩的目标是：在多轮读取文件、执行测试和修改代码之后，控制发送给模型的历史消息和工具输出大小，同时保留继续完成任务所需的信息。

**当前实现（Day 13，以及 Day 14 已接入的校验部分）**：

1. 系统 Prompt 保持原样，固定 `KeepRecentTokens = 20000`，从后向前估算 token，并按完整消息或完整工具批次选择接近预算的保留边界。始终至少保留最新的一个整体，因此单条消息或工具批次很大时，近期原文可能超过 20k；该常量不可配置。
2. 旧历史完整序列化为带角色标记的文本，包括工具名称、参数、调用 ID 和结果。摘要输入不做额外字符截断；工具执行阶段原有的输出大小限制继续生效。
3. 使用当前模型的独立、无工具、非流式 `Provider.Chat` 请求，借用 pi 的首次摘要和更新摘要 Prompt。首次生成摘要，再次压缩时把已有摘要与新增旧历史一起输入，生成更新后的摘要。
4. 摘要按目标、约束与偏好、进度（已完成、进行中、阻塞）、关键决策、下一步和关键上下文组织。修改文件、测试状态和错误等信息由 LLM 归纳，暂未提供独立的结构化元数据字段。
5. 摘要请求单独计算预算，扣除摘要指令、已有摘要和固定余量；超预算时按 UTF-8 边界分块，各块依次更新摘要。分块可以跨序列化消息或参数文本，所有剩余内容继续进入下一块；服务端报上下文超限时，拆小当前块继续处理。
6. 完整摘要成功后，候选检查点通过边界和消息序列校验才提交。模型上下文为“系统 Prompt → 带 `<context-summary>` 标记的 user 消息 → 保留的近期原文”，完整原始历史继续保留。清空旧预算校准，后续主对话回复重新校准。
7. 没有可压缩旧消息时跳过模型调用。摘要失败、为空、返回工具调用、结束原因不完整、校验失败或请求取消时，保留旧检查点和原始历史；输出达到长度限制产生的半截摘要不能保存。
8. `provider.ValidateMessages` 统一校验压缩输入、候选模型上下文、Agent 与流式/非流式 Provider 请求，以及存档消息。校验角色字段、调用 ID、工具类型、名称、完整 JSON 对象参数和每批工具结果配对。批次未完成时不能插入其他角色消息；工具结果可按任意顺序返回，连续 user 消息及批次之外的 system 指令合法。同批次重复 ID、孤立或缺失结果等错误在本地返回，并包含消息索引和相关调用 ID。Session 存档继续禁止保存 system 消息。

关键上下文的保留目标包括：

- 用户的明确约束；
- 当前任务目标；
- 已经执行过的关键操作；
- 当前工作区和修改文件；
- 测试失败原因；
- 尚未完成的工作。

Day 14 已接入压缩后、发送模型前的统一消息序列校验，并加入连续压缩的逐项语义验收测试入口。语义验收只在测试阶段运行；真实模型验收尚待通过，详见下文及开发计划。摘要是 LLM 生成的有损归纳；需要精确信息时，仍应重新读取工作区文件。

当前压缩入口：

- 自动触发：固定 `ContextWindow = 256 * 1024`、`ReservedTokens = 16 * 1024`，估算占用严格超过 `245760` token 时触发。使用最近一次主对话 usage 校准已有占用，再计入新增消息、工具调用、结果和工具声明；缺少 usage 时使用本地粗估。新用户输入追加后、每次模型请求前检查，工具批次全部完成后再检查下一次请求。
- 手动触发：用户在输入循环执行 `/compact`。命令不进入对话历史，成功后立即保存摘要和保留的消息；没有可压缩旧内容时提示并跳过模型调用。只支持命令本身，未提供附加摘要指令参数。
- 超限恢复：模型服务明确返回上下文窗口超限时，调用同一压缩函数，仅重试当前主对话请求一次。保留已完成的工具结果和临时附加指令，不重放工具；输出长度限制和普通限流错误不触发该恢复。

普通主对话、轮数上限后的总结和摘要请求均固定使用 `max_tokens = 8192`，不提供输出上限配置。摘要调用和返回的 usage 计入实际任务统计；摘要请求的 usage 不用于校准主对话预算，本地估算也不计入用量统计。

256k 是代码中的窗口假设，程序未自动识别所用模型的实际上下文窗口。最新用户输入或最新工具批次本身过大时，压缩旧历史仍可能无法使请求放入模型窗口。

实现位于 `apps/internal/compaction/`，三个入口的接入位于 `apps/internal/agent/compact.go` 和 `run.go`。pi Prompt 的来源与 MIT 许可保留在 `apps/internal/compaction/prompt.go` 中。

首版不实现跨会话长期记忆、向量检索、全仓库 Embedding 和复杂记忆召回。

#### 连续压缩后的语义验收

测试使用同一固定任务，实际连续压缩三次，并在每轮保存、恢复独立检查点。场景依次为：修改配置后测试失败、修复后全量测试通过、再次修改代码但尚未复测。每轮必须推进保留起点，检查点构造的对话上下文仅包含摘要与近期原文。

- 逐项检查任务目标、不新增依赖及不修改文档的约束、当前工作区、累计修改文件、测试命令、最新测试状态和下一步；路径、命令与当前失败信息要求准确保留。
- Fake Provider 验证事实输入、旧摘要传递、检查点恢复和 Agent 续接；其参考输出用于流程回归。
- 真实模型生成摘要后，使用同一配置模型的独立请求验收含义，允许同义改写，但要正确判断否定方向、历史与最新状态。每个通过项必须引用摘要中的连续原文，报告不能缺项、重复 ID 或使用不存在的证据。
- 真实模型负例包含遗漏目标、反转依赖约束和把尚未复测的最新修改写成已通过。报告格式、证据和截断处理另有本地测试。

入口为 `apps/test/compaction/semantic_test.go` 和 `semantic_live_test.go`。普通 `go test` 默认跳过真实模型测试；从仓库根目录显式启用后读取 `apps/config/config.toml`：

```bash
MINICODE_TEST_LLM=1 go -C apps test ./test/compaction -run TestCompact_LiveSemanticAcceptance -count=1 -v -timeout=10m
```

2026-10-13 的本地回归、全量 race 测试及 `go vet` 已通过；真实模型验收尝试两次，均在首次摘要请求遇到上游 `do_request_failed`，尚未进入语义判定，Day 14 保持进行中。

### 4.4 模型适配

模型适配层负责与模型服务通信：

- 将 Agent 提供的消息历史和系统规则转换为模型请求；
- 随请求发送工具名称、描述和参数结构；
- 接收普通文本回答；
- 接收结构化工具调用；
- 在后续请求中发送 Agent 提供的工具执行结果；
- 处理鉴权、网络、超时和响应解析错误，并转换为统一响应与错误结构。

Agent 维护多轮消息历史，并负责工具审批、执行及记录工具结果。模型适配层负责模型服务通信和协议转换。

**当前实现（Day 13）**：Agent 依赖 `Provider` 抽象，主对话自动使用可选的 `StreamingProvider.ChatStream` 能力，摘要调用非流式 `Chat`；CLI 通过 `provider.New` 按配置创建实现。公共数据包括 `ChatRequest`、`ChatResponse`、消息、工具调用、流式事件与可选用量；服务 HTTP / SSE 业务错误统一为 `APIError`，网络和取消错误保留原有错误链。

目前实际适配器仅支持 OpenAI 兼容 Chat Completions 协议。`model.provider` 可省略或留空，默认为 `"openai"`；当前可显式指定的协议名也只有 `"openai"`。兼容服务可以通过地址、密钥和模型名切换；新增专用协议需实现 `Provider` 并接入配置工厂，Agent Loop 和工具系统无需随之修改。

OpenAI 兼容实现已支持 SSE 流式请求，发送 `stream: true` 和 `stream_options.include_usage: true`，要求响应类型为 `text/event-stream`。解析器按空行读取事件，合并多行 `data`，支持 LF、CRLF、CR、BOM、注释和心跳，并限制单个事件大小。只接受一个索引为 0 的候选回复，收到 `[DONE]` 后返回正常结束；`finish_reason` 后仍继续接收可能单独出现的用量事件。

Agent 按工具索引累积名称与 JSON 参数，流正常结束并校验全部调用后才执行工具。流式错误、提前断线、超时或取消会关闭响应体，不执行该次未完成回复中的工具，也不将半截 assistant 消息写入历史。任务统计和 Langfuse 追踪继续记录完整调用中的用量、耗时与错误。

主对话和轮数上限后的总结自动使用流式能力，无需用户配置，也不提供 CLI 或 Session 开关。Provider 未实现流式能力或明确返回 `ErrStreamingUnsupported` 时，Agent 使用 `Chat`；其他 API、网络和解析错误直接返回，不自动重发非流式请求。上下文摘要使用独立的非流式 `Chat` 请求，不向终端预览摘要文本。Fake Provider 仍可只实现 `Chat`，测试不依赖真实模型服务。

标准输入和标准输出都连接终端时，CLI 在备用屏幕累计文本并实时渲染 Markdown，按 50 毫秒间隔合并后续更新。跨分片或未闭合的 Markdown 格式随新文本重新排版；渲染失败时回退原文。长文本预览保留末尾可见行，窗口尺寸变化时自动重排。每次流结束、错误、超时或取消时停止预览，恢复光标和主屏幕，完整最终回答随后渲染 Markdown。

非交互模式不输出增量预览和过程状态，完整回答保留 Markdown 原文并写入 stdout，会话标识、统计和错误写入 stderr；副作用工具的审批说明和参数仍按现有规则展示。

### 4.5 Agent Loop

Agent Loop 是项目的核心功能，负责以下流程：

1. 接收用户任务；
2. 构造并校验模型上下文，检查预算，必要时生成并校验新检查点，发送前再次校验消息序列，再调用模型；
3. 判断模型是直接回答还是请求工具；
4. 校验工具名称和参数；
5. 判断工具权限；
6. 必要时请求用户批准；
7. 执行工具；
8. 将工具结果或错误返回模型；
9. 重复执行，直到任务完成或停止。

必须支持以下停止条件：

- 模型返回最终回答；
- 用户主动取消；
- 达到最大模型轮数；
- 达到任务超时；
- 模型 API 发生不可恢复错误；
- Agent 内部发生不可恢复错误。

### 4.6 文件浏览工具

首版计划提供以下只读工具：

| 工具 | 功能 |
|---|---|
| `list_files` | 列出工作区中的文件和目录 |
| `read_file` | 按文件和行范围读取文本 |
| `search_text` | 在文件或目录中搜索文本或正则表达式 |
| `git_status` | 查看当前 Git 工作区状态 |
| `git_diff` | 查看当前未提交修改 |

文件浏览工具需要支持：

- 工作区相对路径；
- 文件大小限制；
- 单次输出大小限制；
- 大文件分段读取；
- 明显二进制文件过滤；
- 路径穿越检查；
- 符号链接边界检查。

### 4.7 文件修改工具

首版计划提供：

| 工具 | 功能 | 权限 |
|---|---|---|
| `edit_file` | 精确替换已有文件中的唯一文本块 | 需要审批 |
| `write_file` | 创建新文件或完整写入文件 | 需要审批 |

首版的 `edit_file` 应要求旧文本满足以下条件：

- 旧文本不能为空；
- 旧文本必须存在；
- 旧文本只能出现一次；
- 修改前文件内容必须与读取结果匹配；
- 写入过程尽量采用原子替换。

后续可以增加更强的 `apply_patch` 工具，但不作为 v0.1 的必要条件。

### 4.8 命令执行工具

当前提供 `bash{command}`，通过 `bash -c` 执行；后续可增加接收 argv 的 `run_command`。命令工具用于运行：

- 单元测试；
- 集成测试；
- 构建命令；
- 格式化命令；
- 静态检查命令。

命令工具需要支持：

- argv 参数数组；
- 指定工作目录；
- 超时控制；
- 退出码获取；
- 标准输出和错误输出捕获；
- 输出大小限制；
- 用户审批；
- 命令失败结果回传模型。

当前接入 shell 字符串并通过 `bash -c` 执行，继承启动 CLI 时的工作目录。`bash`、`write`、`edit` 默认在执行前逐次请求用户确认，拒绝后不执行并将结果回传模型；`--yes` 可自动批准。项目不提供 shell 命令内容黑名单、危险命令硬拦截、细粒度命令权限或 argv 模式，当前工作目录也不是文件系统沙箱。

### 4.9 人工审批

工具分为只读工具和副作用工具。

#### 只读工具

默认可以自动执行：

- 列目录；
- 读取文件；
- 搜索代码；
- 查看 Git 状态；
- 查看 Git diff。

#### 副作用工具

默认需要用户确认：

- 修改文件；
- 创建文件；
- 删除文件；
- 运行命令；
- 其他可能改变工作区或系统状态的操作。

审批提示应至少展示：

- 工具名称；
- 目标文件或工作目录；
- 命令或参数摘要；
- 允许和拒绝选项。

### 4.10 运行状态和日志

CLI 需要让用户能够观察 Agent 当前行为，包括：

- 当前任务；
- 当前模型轮次；
- 当前工具调用；
- 工具参数摘要；
- 审批结果；
- 工具执行成功或失败；
- 最终修改和测试结果。

后续可以增加 JSONL 事件日志，用于调试、恢复和评测，但不作为首版阻塞项。

当前交互终端在备用屏幕预览模型增量文本，每次流结束、出错或取消时恢复主屏幕；完整最终回答、工具状态和审批信息在主屏幕展示，工具原始结果回传模型并记录在会话中。每项任务结束时汇总耗时、模型调用次数、工具调用次数，以及完整模型响应提供的输入、输出和总 token，包含上下文摘要请求。模型未提供 `usage` 时明确显示不可用，只有部分响应提供时标记为部分统计。非交互模式不展示预览和过程状态，完整回答写入标准输出，会话标识、任务统计和错误写入标准错误；审批信息仍按现有规则展示。展示方式不改变会话保存流程；压缩后的存档按 4.2 和 4.3 保存完整原始历史与独立检查点，模型读取摘要与近期原文。

## 5. 设计边界

### 5.1 首版包含

- 单 Agent；
- 单任务；
- 单工作区；
- CLI 交互；
- 多轮上下文；
- 轻量级上下文压缩；
- 基础文件工具；
- 命令执行；
- 人工审批；
- 基础安全和资源限制；
- 测试与结果总结。

### 5.2 首版不包含

- Web UI；
- IDE 插件；
- 多 Agent 和子 Agent；
- 长期记忆；
- 向量数据库和全仓库索引；
- 自动 Git commit、push 和 Pull Request；
- 自动部署；
- 复杂任务编排；
- 多工作区并行操作；
- 操作系统级沙箱；
- 后台常驻服务。

## 6. 基础安全要求

首版不是生产级安全沙箱，但必须具备基础防护：

- 文件操作限制在工作区内；
- 拒绝绝对路径和路径穿越；
- 检查符号链接是否指向工作区外；
- 限制文件、请求和工具输出大小；
- 限制模型最大调用轮数；
- 限制命令执行时间；
- 副作用工具默认需要审批；
- 不将未经用户批准的模型命令交给 shell 执行；
- 不在日志中输出 API Key；
- 明确提示：批准执行的命令和构建脚本仍可能执行任意代码，项目不提供危险命令硬拦截。

## 7. v0.1 验收标准

v0.1 至少应完成以下任务：

1. 解释一个陌生仓库的目录结构和启动流程；
2. 找到指定代码并完成一个小型修改；
3. 运行测试并根据失败信息继续修复；
4. 在工具参数错误时能够重新观察和调整；
5. 用户拒绝写入或命令执行后，操作确实不会发生；
6. 最终准确说明修改内容和真实验证结果；
7. 长任务上下文接近限制时能够进行轻量级压缩；
8. 超过最大轮数或任务超时后能够安全停止。
